Security architecture and delivery plan

REST secret retrieval API

Add a read-only, API-key authenticated interface for applications to retrieve typed secret data from a selected project and shared environment, while making the necessary change to Nebula's current client-only decryption boundary explicit and controlled.

Convex HTTP actions JSON over HTTPS Scoped API keys Development / UAT / Production Read-only v1
01 / Recommendation

Implement a narrow retrieval gateway, not a second general-purpose backend

Expose versioned routes from convex/http.ts. Authenticate each request with a high-entropy, revocable API key; authorize it against explicit project, environment, and optional secret grants; retrieve ciphertext through internal Convex functions; decrypt only inside the HTTP action; return a typed JSON response; and append a privacy-safe service audit event.

!
This feature changes the encryption trust model.

Today, values are encrypted and decrypted in the browser and the backend never receives readable secret values. A REST API that returns plaintext JSON requires a trusted server-side decryption identity. The implementation must therefore add an API decryption key, wrap each shared environment key for that identity, and accept that the Convex HTTP runtime can see plaintext during a successful request. This is an architectural approval gate, not a hidden implementation detail.

Recommended v1

Read-only, server-decrypted JSON

Supports application consumption directly, with tightly scoped keys and no write endpoints.

Preserve

Existing browser encryption

Interactive users continue to encrypt and decrypt locally. The service identity receives only shared environment envelopes.

Explicitly excluded

Local environment

Local values are user-owned. They must not be exposed to application API clients or wrapped to the service identity.

02 / Current state

What the repository already provides

The API can reuse the existing data model and cryptographic format, but it cannot reuse browser-only private keys. The plan below is based on the current schema and implementation, not a greenfield design.

Recommended
D2

Minimal schema
D4

Offer one-secret retrieval plus a paged environment snapshot. The single-secret route is the safer default for narrowly scoped consumers.

Practical
D5

Every client grant names one project and one environment. An optional separate allowlist limits it to specific secret cryptoId values.

Least privilege
D6

Generate at least 256 bits of random secret material, store only a keyed digest, and return the full credential once.

Required
D7

Required
D8

The JSON API returns secret payload fields only. Encrypted attachments require a separate streaming/download design and are excluded from v1.

04 / Architecture

Request and trust boundaries

A Convex HTTP action is the public edge. Database reads and audit writes remain internal functions. The action alone handles the presented API secret and unwrapped key material.

01 / CALLER Consumer application Sends HTTPS GET with a bearer API key. Keeps the credential in its own secret store.
→
02 / EDGE Convex HTTP action Parses key, hashes secret material, validates request, applies rate limit, and coordinates the response.
→
03 / DATA Internal Convex query Checks client/key/grants and returns only the permitted encrypted rows plus the matching service envelope.
→
04 / CRYPTO In-memory decrypt + JSON Unwraps keys, verifies AES-GCM/AAD, validates payload shape, writes an audit event, and responds with no-store headers.
New trusted zone: the Convex deployment, its API decryption private key, its API-key digest pepper, and anyone able to deploy code or read those environment variables can potentially decrypt shared environment values. Production access, deploy rights, logs, and backup/recovery procedures must be treated accordingly.
Key enrollment

Wrap environment keys to a service public key

  1. Generate an RSA-OAEP service key pair outside the browser device-key flow.
  2. Store the private JWK in the Convex deployment environment, not in the database or source control.
  3. Expose the public JWK to a System Administrator enrollment screen.
  4. An authorized browser unwraps each shared environment key and re-wraps it to the service public key.
  5. Store only the resulting service envelopes and key metadata in Convex.
Rotation

Version both the key pair and envelopes

  • Assign an opaque serviceKeyId to every service public/private pair.
  • Keep old private keys available while active data still references their envelopes.
  • Enroll the new public key and verify decryption before making it active.
  • Retire old private material only after re-wrapping all active environment key versions and testing rollback.
05 / REST contract

Versioned endpoints and deterministic JSON

v1 uses GET-only routes. Values are returned under data so secret-type-specific fields can evolve without changing the common envelope.

GET
/api/v1/projects/{projectId}/environments/{environment}/secrets/{cryptoId}

Retrieve one active secret. The API key must have a matching project/environment grant and, when configured, an explicit grant for this secret.

GET
/api/v1/projects/{projectId}/environments/{environment}/secrets?cursor={cursor}&limit={1..100}

Retrieve a bounded environment snapshot for the project. Default limit: 50. The continuation cursor is opaque. Only active, granted secrets with values are returned.

GET
/api/v1/health

Unauthenticated liveness only: returns status and API version. It must not report key enrollment, database, project, environment, or secret details.

Example request

Host: <deployment>.convex.site
Authorization: Bearer nbs_live_4K9W2R.qB7...256-bit-secret
Accept: application/json

06 / API-key authentication

API clients are first-class principals

Do not model an application as a fake human user. Give it a named client record, one or more independently revocable keys, and explicit grants.

Credential

Structured key format

nbs_live_{keyId}.{secret} lets the server perform one indexed lookup without storing or scanning the secret. Use a separate nbs_test_ prefix only if deployments share operational tooling.

Storage

Keyed digest only

Store HMAC-SHA-256(API_KEY_PEPPER, fullKey), prefix, status, expiry, and metadata. Compare digests in constant time. Never store the full key.

Lifecycle

Create, rotate, revoke

A System Administrator creates a key, sees it once, overlaps old/new keys during rotation, and revokes the old key after the consumer changes.

ControlPlanReason
EntropyAt least 32 cryptographically random bytes for the secret portion.Prevents offline guessing even if the digest table is copied.
PresentationAuthorization: Bearer only; reject query-string credentials.URLs leak through logs, history, proxies, and monitoring.
ExpiryRequired, with a recommended maximum of 90 days and a visible owner/rotation note.Limits the lifetime of forgotten credentials.
ScopeOne or more project/environment grants, plus optional secret allowlist rows.A production key should not automatically read development/UAT or every project.
RevocationChecked on every request; no positive credential cache in v1.Revocation takes effect immediately.
Usage trackingAppend retrieval audit rows; update summary usage asynchronously or in a separate low-contention record.Avoid write contention on the key record during traffic bursts.
Rate limitingUse the Convex rate-limiter component per API key and a coarser per-IP/deployment safety limit.Avoid hand-rolled counters and contain stolen-key abuse.
A
Administration remains under WorkOS.

Key creation, grant changes, rotation, and revocation should be authenticated human operations restricted to System Administrators, with step-up confirmation for production grants. The machine API itself must not contain endpoints that can create or expand its own credentials.

07 / Schema

New tables and one audit migration

Keep grants normalized and indexed. Avoid arrays of projects, environments, or secret IDs on a client document because they grow without bound and force whole-document rewrites.

Table / changeKey fieldsIndexes and invariants
apiClients name, description?, status, createdBy, createdAt, updatedAt Index by status. A client is a durable machine identity; key rotation does not change its grants.
apiKeys apiClientId, unique keyId, digest, displayPrefix, status, expiresAt, creation/revocation metadata Indexes by keyId and by client/status. Unique key ID. Full key is never persisted.
apiClientEnvironmentGrants apiClientId, projectId, shared environment, mode (allSecrets or allowlist), status and grant metadata Unique/indexed by client + project + environment. Validator excludes local.
apiClientSecretGrants environmentGrantId, secretId, status and grant metadata Unique/indexed by grant + secret. Used only when the parent grant mode is allowlist.
apiServiceKeyEnvelopes serviceKeyId, shared environment, environmentKeyVersion, wrappedKey, status, enrollment metadata Unique/indexed by service key + environment + environment key version. Contains no private key.
apiRetrievalEvents apiClientId, apiKeyId, project, environment, secret ID or result count, outcome, reason code, request ID, timestamp Append-only; indexes for client and created time. Never store values, names, bearer data, IP addresses by default, or decrypted error details.
auditEvents actor change Make actorUserId optional and add a discriminated actor representation for user or apiClient. Use widen-migrate-narrow so existing human events remain readable. Alternatively keep high-volume API retrievals in the separate table above and record only API administration in auditEvents.
I
Index-driven reads

The retrieval query must start from the key ID and exact grant index, then the project's active secret definitions, then the existing secret/environment/owner index. Do not scan API keys, grants, or all secret values and filter in memory. The bulk route must use bounded pagination and a hard response-size guard.

08 / Request processing

Fail closed at every stage

The order matters: reject malformed or unauthorized requests before loading encrypted payloads, and do not report which security check failed.

Step1

Normalize the request

Accept GET only, enforce a small header/path budget, create or validate a request ID, parse the exact v1 route, reject local, and validate IDs/cursor/limit without reflecting attacker input.

No database read
Step2

Authenticate the key

Parse the bearer format, derive the HMAC digest in the action using the deployment pepper, and use keyId for an indexed internal lookup. Check constant-time digest equality, client/key status, and expiry.

401 on failure
Step3

Apply limits and authorize scope

Consume a per-key rate-limit token. Resolve the exact active project/environment grant and optional secret allowlist. A scope miss is returned as not found so the key cannot enumerate other projects or secrets.

Before ciphertext
Step4

Load a bounded encrypted result

An internal query retrieves active definitions, shared values (ownerUserId: null), versions, and the active service envelope. The bulk route uses native Convex pagination and stops before the response-size ceiling.

Internal query
Step5

Decrypt and validate

Import the service RSA-OAEP private JWK, unwrap the environment AES-KW key, unwrap each data key, rebuild AAD with owner shared, perform AES-GCM decryption, parse unknown JSON, and validate it against the secret type.

Request memory only
Step6

Audit and respond

Append a success or safe failure event with client/key/project/environment/secret identifiers and request ID. Return deterministic JSON with no-store headers. Clear references to plaintext/key buffers as soon as practical and never log the response.

200 or safe error
09 / Security

Threat controls and non-negotiable rules

API keys are bearer credentials: possession is authority. The design limits what a stolen key can read and makes its use visible, but it cannot stop an authorized caller from copying returned plaintext.

Credential theft

Contain scope and lifetime

  • Project/environment/secret grants, short expiry, immediate revocation, and overlapping rotation.
  • No wildcard that silently includes future production projects.
  • Optional IP/CIDR allowlist only as an additional control, not identity.
Resource enumeration

Uniform public failures

  • Do not distinguish nonexistent from out-of-scope project/secret resources.
  • Do not reveal client name, key status, expiry, environment enrollment, or secret type on failure.
  • Keep response time broadly consistent for credential errors.
Plaintext leakage

Keep values out of the platform exhaust

  • Never log headers, bodies, decrypted payloads, decryption exceptions, or key material.
  • Disable response caching and inspect proxy/APM defaults before release.
  • Use canary values in tests to prove they do not enter Convex records or logs.
Privileged deployment compromise

Harden the new trusted server

  • Restrict Convex deployment and environment-variable access; require MFA and reviewed releases.
  • Separate development, UAT, and production service keys and API-key peppers.
  • Document emergency private-key and API-key rotation.
Denial of service

Bound every operation

  • Rate-limit per key and deployment; cap page size, decrypted bytes, and response bytes.
  • Reject huge headers and malformed cursors before database work.
  • Avoid unbounded collect(), nested project-wide N+1 scans, or per-request writes to one shared document.
Cryptographic mismatch

Reuse one canonical implementation

  • Move shared AAD and payload validation into runtime-neutral code used by browser and HTTP action.
  • Test every secret type and version with known vectors.
  • Fail on unsupported algorithm, AAD version, key version, or payload shape; do not coerce.
X
Never place a decryption key or API key in Vite client variables.

Anything prefixed for the frontend is public. API_DECRYPTION_PRIVATE_KEY_JWK and API_KEY_PEPPER belong only in the Convex deployment environment and must have distinct values per deployment. They must not be stored in .env files committed to the repository, Vercel client settings, the database, or the browser.

10 / Delivery

Phased implementation and review gates

The sequence keeps the application deployable and prevents a half-configured API from becoming public. Each phase should be a reviewable change with tests.

Phase0

Approve the trust and product contract

Confirm that server-side plaintext is acceptable; approve shared environments only, REST routes, response shape, client ownership, expiry, bulk retrieval, and attachment exclusion.

Architecture gate
Phase1

Widen the schema

Add client/key/grant/service-envelope/retrieval-event tables and indexes. Widen audit actors if using the shared audit table. Deploy without routes enabled; add bounded migrations only where existing rows need new actor fields.

Deploy 1
Phase2

Build administration and key enrollment

Add WorkOS-protected System Administrator functions/UI for clients, API-key creation/one-time display, grants, revocation, expiry, and service public-key enrollment. Record all changes in the human audit trail.

No public retrieval
Phase3

Extract and test shared cryptography

Move canonical AAD, base64, encrypted-payload types, decryption, and payload validation into runtime-neutral modules. Add cross-runtime known-vector tests proving browser-encrypted values decrypt identically in the action.

Crypto review
Phase4

Implement internal API services

Create internal indexed lookup, authorization, retrieval, service-envelope, and audit functions. Add the official Convex rate-limiter component. Test revoked/expired keys, every grant combination, local rejection, archive behavior, and pagination.

Backend tests
Phase5

Add the v1 HTTP router behind a kill switch

Implement exact routes, request validation, keyed digest, decryption, JSON/problem responses, headers, response limits, and a deployment-level SECRETS_API_ENABLED fail-closed switch. Do not enable production yet.

Deploy 2
Phase6

Pilot in development, then UAT

Enroll separate service keys, create a narrowly scoped test client, verify consumer integration and rotation, inspect redacted logs/audits, run abuse and canary tests, and document on-call/rollback steps.

Operational gate
Phase7

Enable production deliberately

Provision production-only private key and pepper, enroll production environment envelope from an authorized device, create the first expiring production client/key, test one secret, monitor denials/latency/failures, and then enable intended consumers.

Release gate

12 / Verification

Definition of done

Release only after the tests prove both positive retrieval and negative isolation. The important property is not merely that a valid key works, but that changing any identifier cannot expand its authority.

Authentication matrixMissing, malformed, unknown, expired, revoked, and wrong-deployment keys all return the same safe 401 contract.
Authorization matrixClient x key x project x environment x grant mode x secret combinations allow only the exact intended rows.
Local isolationNo API client can read, grant, enroll a service envelope for, or infer local environment values.
Cryptographic compatibilityValues encrypted by the current browser code decrypt in the HTTP runtime for every supported type and version.
Integrity failureModified ciphertext, IV, wrapped key, type, owner, environment, ID, or version fails without returning partial data.
LifecycleKey creation shows plaintext once; rotation overlaps safely; revoke and client suspension deny the next request.
Archive behaviorArchived projects/definitions and missing environment values return the agreed generic not-found response.
Pagination and boundsBulk reads are stable, bounded to 100 items and the byte ceiling, and continue with an opaque validated cursor.
Rate limitingPer-key quotas behave under concurrency and return 429 plus Retry-After without affecting other clients.
Audit completenessSuccess and denied/failed retrievals contain safe identifiers, reason code, timestamp, and request ID with no secret content.
Plaintext canariesKnown values never appear in database records, logs, analytics, errors, URLs, source maps, or persistent server caches.
HTTP contractRoutes, status codes, content types, no-store headers, request IDs, health response, and JSON fields match the documented v1 contract.
Deployment isolationDev/UAT/prod use different private keys, peppers, API keys, clients, envelopes, and URLs; credentials do not work across deployments.
PerformanceSingle-secret p95, page p95, documents read, bytes read, decrypt time, and audit latency meet agreed budgets under expected concurrency.
✓
Build and release gate

pnpm test, pnpm run lint, pnpm run build, and a one-shot Convex validation/deploy check must pass. Then run a real HTTPS smoke test with a temporary, minimally scoped key and revoke it immediately after verification.

13 / Operations

Deployment, monitoring, and rollback

The API is operationally sensitive because it can produce plaintext. Configuration drift or a logging change should disable retrieval rather than degrade security.

Convex environment variables

Server-only configuration

  • SECRETS_API_ENABLED - explicit fail-closed switch.
  • API_KEY_PEPPER - random per deployment.
  • API_SERVICE_KEY_ID - active private-key identifier.
  • API_DECRYPTION_PRIVATE_KEY_JWK - encrypted/secret control-plane value.
  • Optional response byte, rate, and page limits with secure defaults in code.
Signals

Monitor without secret content

  • Request count and latency by route/outcome/environment, not secret name.
  • 401/404/429/5xx rates, digest failures, decryption reason codes, and rate-limit exhaustion.
  • Key expiry horizon, clients without owners, service-envelope readiness, and zero/duplicate active service keys.
  • Never attach request/response bodies or Authorization headers to APM traces.
Rollback

Disable before reverting

  1. Set SECRETS_API_ENABLED=false.
  2. Revoke affected API keys/clients.
  3. If private material may be exposed, rotate the service key and re-enroll envelopes.
  4. Preserve safe audit/retrieval events for investigation.
  5. Revert application code only after traffic is stopped; do not delete schema rows during the incident.
Consumer runbook

Handle credentials like production secrets

  • Store the API key in the consumer's secret manager, never source control or client-side code.
  • Use short timeouts, bounded retries with jitter, and do not log response bodies.
  • Cache only in process if the application explicitly accepts the risk and honors a short TTL.
  • Rotate before expiry and prove the new key before revoking the old one.
V
Deployment note

The REST API is hosted by the Convex .convex.site deployment, so it does not require a Vercel server function. If this project continues to deploy its Vite frontend to Vercel, ensure the package build command still triggers the required Convex deployment, create a Convex deploy key, and add that deploy key as a protected Vercel environment variable.

14 / Clarification questions

Questions to resolve before implementation

The plan records a safe default under each question so review can continue. The first question is the only architecture blocker.

  1. Is it acceptable for the Convex HTTP runtime and deployment administrators to gain the technical ability to decrypt shared environment secrets?Plan assumption: yes, provided the private key is deployment-only, access is tightly restricted, use is audited, and local values remain client-only.
  2. Should consumers retrieve one secret at a time, an entire project/environment snapshot, or both?Plan assumption: both, with one-secret retrieval preferred and the snapshot route paged/capped.
  3. Should access be scoped only by project and environment, or must individual-secret allowlists be mandatory for production?Plan assumption: allow both grant modes; recommend individual-secret allowlists for production consumers.
  4. Who may create API clients and grant production access: System Administrators only, or ordinary Admins as well?Plan assumption: System Administrators only for all key and grant operations.
  5. What key expiry and rotation policy is required?Plan assumption: expiry is mandatory, maximum 90 days, with overlapping rotation and owner metadata.
  6. Are callers server-to-server only, and are browser-based calls explicitly prohibited?Plan assumption: server-to-server only; no permissive CORS and no API keys in frontend JavaScript.
  7. Are attachments required through this API?Plan assumption: no; v1 returns only decrypted JSON payload fields.
  8. Do production clients need IP/CIDR restrictions in addition to API keys?Plan assumption: optional defense in depth, subject to caller infrastructure having stable egress addresses.
  9. What are the expected request rate, number of secrets per project, maximum payload size, and freshness requirement?Plan assumption: low-to-moderate service configuration traffic, 50 items by default, 100 maximum per page, no shared response cache, and immediate revocation.
  10. Should API client administration be added to the existing application UI in the first release, or may initial provisioning use protected backend functions/CLI?Plan assumption: include a minimal System Administration UI so one-time key display, grants, expiry, and revocation are visible and auditable.
